# diagram-data

Answers "what is the shape of the data?" Cardinality is where hand-drawn ER
diagrams lie: one-to-many drawn as one-to-one, an optional key drawn as
required. This skill reads both from the schema. For SQL it generates the
diagram; for ORM models it traces each entity to its definition.

`<engine>` is `${CLAUDE_SKILL_DIR}/../diagram-review/scripts`; shared rules
live in `${CLAUDE_SKILL_DIR}/../diagram-review/references/`.

## Workflow

### 1. Find the schema of record

In this order: migrations (`db/migrations/`, `migrations/`, `prisma/migrations/`),
then a schema dump (`schema.sql`, `structure.sql`), then the ORM models
(`models.py`, `schema.prisma`, `app/models/`, `*.entity.ts`). Migrations
replay to the current schema; models can drift from it. Say which one you
used.

### 2. Scope it

Pick the tables the question is about. A whole schema is rarely one
diagram. The node cap (7, 12 or 20 by reader level, `levels.md`) means one
area per diagram: orders, accounts, billing. Beginners get entities and
relationships only, no columns.

### 3. Generate or trace

**SQL DDL or migrations:** generate.

```bash
python3 <engine>/schema_er.py db/migrations --tables customers,orders,order_items \
  --level intermediate --title "Orders data model" --markdown
```

Add `--no-attributes` for a beginner view. The output reads cardinality from
the DDL:

- a NOT NULL foreign key means exactly one parent: `}o--||`;
- a nullable one means zero or one: `}o--o|`;
- a unique one means one-to-one: `|o--||`.

Every table gets a `%% ref ... = schema:<file>#<table>`, and a key line
explains the notation.

**ORM models:** write an `erDiagram` by hand, and trace each entity with
`%% ref <Entity> = schema:<models file>#<ClassOrModel>`. Read cardinality
from the field definitions (`ForeignKey(null=True)`, `@relation`, `?`
optional markers, `unique=True`), never from the names. Use `classDiagram`
only when the models carry behaviour the reader needs to see.

### 4. Check

Run the three checks in `checks.md`. The truth check confirms every entity is
defined in the file its ref names.

### 5. Explain

Lead with the one-line shape ("A customer has many orders; each order has
line items that point at products"). After the diagram, read each
relationship in words in both directions, and call out the optional ones,
because that is where bugs live. Then the key line for the cardinality
marks. A beginner gets nouns and "has many", and no PK or FK. An advanced
reader gets keys, nullability and the indexes that matter.

### 6. Persist, when it documents the system

The data model belongs in the Spec or Reference that owns the schema
(`persisting.md`). Keep the `%% generated by` line, so readers regenerate
after a migration rather than hand-editing. Run `lore check`.

## What not to do

- Do not infer relationships from column names alone (`user_id` with no
  foreign key is not a relationship; say it is an unenforced reference).
- Do not show every column at beginner or intermediate level; show the
  keys and the columns the question is about.
- Do not mix tables from different databases without saying so.
